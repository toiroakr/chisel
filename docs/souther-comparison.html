check と verify が保証すること

verify は構築と事後条件の証明、check --strict はその証明に加えて例の一致と必要な網羅を確認する。verify だけの成功では、例の充足を確認したことにはならない。

状態check --strictverify
成功satisfied：例・測定・構築の証明を満たす。adequate: true。verified：途中の構築・結果・副作用・ensures の証明が成立。
違反や不足が確定not_satisfied：例の不一致、到達可能な未網羅、構築の反例など。終了コードは非 0。refuted：構築や事後条件に違反する反例がある。終了コードは非 0。
確定できないundetermined：未測定・未証明が残る。adequate: false、終了コードは非 0。undetermined：未対応の式や探索・評価上限で証明を確定できない。終了コードは非 0。

サンプルが成功しただけでは verified にしない。有限領域をすべて調べ終えた場合か、対応する制約の証明が成立した場合にだけ構築を verified とする。実際の違反が見つかれば、全領域の探索が終わる前でも反例として報告する。

残る保証の制約

任意の TypeScript コールバック、一般の量化を含む構築、関数依存の全入力保証は未対応。合成した実装は段間の入力条件も検査し、その条件を証明できなければ未判定になる。式 API への移行だけですべての実装を証明できるわけではない。これらは未判定として strict / verify を失敗させる。Souther と証明できる式の集合が同一であることは確認していない。

設計判断が違うところ

機能の追加後も、専用言語と TypeScript ライブラリで保証の境界は異なる。差を隠して互換と扱わず、採った設計と移行時の影響を残す。

移行するときに変わること

任意の run を model の式に置き換え、if を choose、途中のデータ構築を construct にする。名前付きデータを作るモデルでは constructs を宣言する。既存コールバックを残した段階は実行と適合検査ができるが、strict は通らない。

const implementation = c.implement(definition, {
  cases: {
    request: c.model("count", input => ({
      result: c.arithmetic("add",
        c.choose(input.first.$eq(true), 1, 0),
        c.choose(input.second.$eq(true), 1, 0)),
      effects: [],
    })),
  },
});

上はモデル定義の抜粋。完全な例では、2 つのフラグの 4 通りに対して結果 0 / 1 / 1 / 2 を明示する。リポジトリ直下で次を実行すると、ビルド・構築証明・例と網羅の厳密な検査を再現できる。

npm run check
npm run build
node dist/cli.js verify examples/verified.spec.ts
node dist/cli.js check examples/verified.spec.ts --strict --timeout 30000

4 通りの例を含む、strict が通る実装 · エディタのビルドタスク例 · 詳しい API と移行方法

既定の意味が変わる箇所

未判定でも true だった adequate を廃止。実現可能な pair の不足は不合格。文字列は NFC とコードポイント単位。CLI は時間制限を持つ。JSON レポートには pairs の義務と constructions の証明結果が加わる。
