# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

Chisel is an experimental TypeScript toolkit for growing an executable business specification from a closed data model, generated examples, and human-provided expectations. The workflow is fixed and sequential:

```
declare data and behavior
→ generate unanswered examples
→ let a human fill expected results
→ refine data and behavior
→ implement an executable model
→ check the model against the examples
```

Requires Node.js >= 26 (uses the built-in `Temporal` API — see `mise.toml` for the pinned version).

## Commands

```sh
npm run typecheck   # tsc --noEmit
npm test            # vitest run (see vitest.config.ts: test.include is test/**/*.test.ts)
npm run check        # typecheck + test
npm run coverage     # vitest run --coverage (v8 provider, src/** only)
npm run build        # tsc -p tsconfig.build.json -> dist/
npm run demo         # runs examples/progressive-demo/run.ts end-to-end
```

CI (`.github/workflows/check.yml`) runs `npm ci && npm run check` on push to `main` and on every pull request.

Run a single test file directly with vitest, e.g. `npx vitest run test/chisel.test.ts`. Tests use Vitest (`describe`/`it`/`expect` imported explicitly from `"vitest"`, no globals). `expect(...).toStrictEqual(...)` (not `toEqual`) is the standard equality assertion here — it distinguishes `{ note: undefined }` from `{}` the same way `node:assert.deepStrictEqual` did, which matters for the `optional()` invariant below.

Every named construct takes its name as the first argument — `behavior(name, {...})`, `spec(name, {...})`, `action(name, {...})`, `compose(name, [...])`, `external(behavior, reason)` aside. The public API is meant to be used as a namespace (`import * as c from "chisel"`), like zod's `z` and valibot's `v`: README, `examples/` and `generate`'s output write `c.variants(...)`, `c.action(...)`, `c.check(...)`; tests keep named imports. The four entry points are `check` (adequacy of a specification, what `chisel check` prints), `generate` (the rows no row stands in yet, `{ rows, notComposed }`, what `chisel generate` prints), `test` (the answered rows run against production code, returning the rows that disagree) and `perform` (run the model once on one input).

`src/cli.ts` defines its commands with [`@politty/zod`](https://www.npmjs.com/package/@politty/zod) (politty's zod flavor; argument schemas are zod, and the file argument carries its own missing message so it reads `Missing required argument <file>`) and exports the root command as `cli` (`chisel` with `check` / `generate` subcommands). Handlers print with `console.log` and signal failure by throwing — politty turns a thrown error into exit code 1 (`runMain` prints it as `Error: <message>` on stderr). There is no other exit code: `--strict` inadequacy, a spec file exporting nothing, an unknown subcommand, and a missing `<file>` all exit 1; bare `chisel` prints help and exits 0. A top-level `isRunAsScript()` guard (comparing `import.meta.url` against the `realpathSync`'d `process.argv[1]`, so it resolves correctly through the `dist/cli.js` bin symlink too) calls `runMain(cli)` only when the file is executed directly. `test/cli.test.ts` drives `cli` in-process with `runCommand(cli, argv, { captureLogs: true })` for nearly all cases (fast, fully covered by `npm run coverage`), reading handler output from `result.logs.entries` and failures from `result.exitCode` / `result.error`, and keeps exactly one `spawnSync` subprocess test to prove the shebang/`isRunAsScript`/`runMain` wiring itself works end-to-end — that one test's process boundary is the only part of `cli.ts` Vitest's V8 coverage can't see.

The CLI can load `.ts` spec files directly (via `tsx/esm/api`'s `tsImport`), no build step required:

```sh
npx tsx src/cli.ts check ./examples/order-cancellation.spec.ts
npx tsx src/cli.ts check ./examples/order-cancellation.spec.ts --strict
npx tsx src/cli.ts generate ./examples/order-cancellation.spec.ts
```

package.json also exposes these as `npm run example:check`, `npm run example:strict`, `npm run example:generate`. `check` reports state without failing by default; `--strict` exits 1 when examples are unanswered, variants are uncovered, the implementation is absent/pending, control policies are incomplete, or the implementation disagrees with an example.

## Architecture

Everything is exported through `src/index.ts`; there is no barrel re-exporting beyond that. Four modules, each building on the last:

1. **`src/schema.ts`** — the data layer. `Schema<T>` is the common interface (`parse`/`placeholder`). Primitives: `string`, `number`, `int`, `boolean`, `instant` (Temporal.Instant), `literal`, `array`, `record`; any schema becomes optional with the `.optional()` method (there is no free `optional` function; the method is typed through `this` so that `Schema<T>` stays covariant in `T`). Every schema takes `.refine(v => v.gte(1))`: the callback receives a symbolic term (from `src/rule.ts`, a Proxy: a key with a `$` prefix reads that field, `v.$start`, so no field can shadow a method, and `length()` measures it) and returns a `Rule` made with the term's methods `lt`/`lte`/`gt`/`gte`/`eq`/`ne` (and `all`/`any` over array elements), combined with the rule's own non-enumerable `and`/`or`/`not`, which `parse` enforces and `placeholder` satisfies. There are no free functions for these; `Condition` types the combinators. Numbers (`number`, `int`) also take the shorthands `min`/`max`/`gt`/`lt`, and strings, arrays and records `min`/`max`/`length` (on the length); each desugars in `refinable` to the rule `refine` would take (`int().min(1)` is `refine(v => v.gte(1))`, `array(x).min(1)` is `refine(v => v.length().gte(1))`), so borders are drawn alike. A comparison whose operand is absent (an optional field left out) holds. Inside `of.all(each)`/`of.any(each)` the element term is rooted at a name for the element (`#each<depth>`, by nesting depth so it reads the same in every module graph), and `holds` evaluates `each` against the enclosing scope with the element bound under that name (`bindElement`), so a term from outside the quantifier is read against the scope it was written in. `describeRule` and the guard analysis (`Frames` in `src/guard-borders.ts`) resolve an element name to the element's own scope, path and label, and everything else to the enclosing frame. Terms are tagged with `Symbol.for`, because the CLI loads spec files in a separate module graph. `object(shape)` composes fields and refuses a key its shape does not declare (`Unexpected key` at `$.<key>`; `variants` takes its discriminant off before handing the value to the case's object, unless that object declares the discriminant itself); `.optional()` fields become real `key?: T` in the inferred type (via `InferShape`), not a required `key: T | undefined`. `variants(discriminant, variants)` builds a tagged union over object variants and is central to the whole system: behaviors' `input` and `effects` must be `VariantsSchema` because coverage analysis is driven by enumerating `variantTags` — `array`/`optional`/`record` are only meant to appear *inside* an `object()` shape or as a behavior's `result` schema, never as a behavior's `input`/`effects` directly. `tagOf`/`isVariantsSchema` are the primitives everything else uses to identify which variant a runtime value belongs to.

2. **`src/behavior.ts`** — the behavior/implementation layer. `behavior(name, { input, result, effects })` declares a boundary (data in, data out, side-effect vocabulary) without implementation. `implement(behaviorDef, { cases, controls })` supplies one action (or `todo(reason)`) per input variant, plus a `ControlTable` mapping each effect variant to a `ControlPolicy` (`execution: direct|outbox|queue`, `idempotency`, `compensation`, optional `exposure`) or `todo`. `perform` dispatches on the input's discriminant tag, runs the matching decision, and validates the input/result/effects against their schemas — throwing `SpecificationError` on any mismatch, missing case, or pending decision. A case is written as `action(id, { guards?, run })`: `guards` (optional) is a builder returning `guard(condition, orElse)`s whose conditions are `Rule` data built with the term methods (`line.$quantity.lte(line.$stock)`, `lines.length()`, `lines.all(line => …)`, `a.and(b)`/`a.or(b)`/`a.not()`), and `run` answers once every guard holds. It builds a `RulesDecision` (`kind: "rules"`, `run` stored as `otherwise`); an action with only `run` is measured as a decision with no branches — whatever branching `run` does internally is trusted, not read, exactly as the answer after the guards always was. `id` is the action's name in reports. A free-form `Decision` object (`kind: "decision"`, an opaque `run`) is still accepted and is what makes arms `not measured`, but the docs no longer present it. `run` may be a `match(input => input.$field.$discriminant, { tag: handler })` — `match` takes the selected discriminant's literal union as its `Tag` type parameter and types `cases` as exactly those keys, so a missing or unknown case fails to compile; `implement` still refuses at run time a match whose selector is not a sum field's discriminant (a plain string field makes `Tag` `string`) or whose cases are not exactly that sum's cases, since the arms measure only sees the keys written. A guard's `orElse` is an ordinary result case — business rejections are never exceptions or a Result wrapper, following Souther — so preconditions such as an empty or already confirmed cart stay input cases that answer a rejection. `runTraced` also returns the arms taken, every comparison evaluated (with the scope it read), and the way through the guards; `comparisonsReached` gives the comparisons synchronously for `generate`. `action` infers its types from the case it is written for only (`NoInfer`). `implement`'s options are `NoInfer` as a whole, and so is `B` in its return type (`Implementation<NoInfer<B>>`): `B` must come from the definition alone. Without the latter, an `implement(...)` written inline inside `spec` took `B` from the specification's contextual return type (still `AnyBehavior` while `spec` infers its own `B`), and the literals in its `action` widened. `Tags`/`VariantOf` match `VariantsSchema<any, …>` — a literal discriminant is not assignable to `VariantsSchema<string, …>`, and that mismatch once made `Tags` `never` for every sum and silently disabled type-checking of `cases`.

A behavior may declare `ensures: clause => [clause.when(name, cases, (input, value) => rule), clause.always(name, …)]`, relating the input to the answer (a clause must name both roots). It is held wherever an answer is written or produced: implementation answers throw `SpecificationError`, answered example rows and conformance-subject answers become failures. A conjunct comparing the input with a constant (or two inputs) draws an `ensures` border, met by any answered row writing the value. Clause names are distinct within a behavior (`behavior` throws on a repeated one). `report.ensures` (`src/ensures.ts`) classifies every conjunct of every rule the way Souther does — `derivable` (numeric or instant terms), `exact match` (`==`/`!=` over strings, booleans, literals or discriminants), `always holds`/`never holds` (a rule that settles without the answer: constants, or a term compared with itself), `runtime only` (everything else, including `all`/`any`/`or`/`not`) — and lists the result cases no clause names (`unstated`, empty when no clause is declared or one is written with `always`). What a caller may assume after matching a case has nothing to seed in Chisel: there is no static checker over an implementation's constructions, every stage's answers are already held to its clauses at run time, and a composition measures no arms or ways of its own.

`requires: { name: dependency(outputSchema) | dependency(inputSchema, outputSchema) }` (`src/dependency.ts`) declares injected dependencies. Decisions and rules handlers receive the resolved dependencies as a second argument (`BehaviorDeps<B>`). An action's `guards` builder also gets a second argument, a term over the value dependencies (`ValueDepsOf`, function dependencies left out) rooted at `DEPS` (`"#deps"`); guards are evaluated against `withDeps(input, deps)`, i.e. the input with the dependency values under `#deps` (carried into `all`/`any` elements too), so a comparison reached records them. For measurement `guardScope` adds a `#deps` field of the value dependencies' output schemas to the case's schema, so borders, unread comparisons and feasibility read a dependency like a field; a border between a position and a dependency is named `deps.<name> − @case.<field>`, and `generate` composes it by moving the position against the stand-in the origin row writes with `with` (threaded through `comparisonsReached`/`traceSync`/`compose`). Rows stand in for value dependencies with `with`, and a specification's `fakes: [fake(behavior, name, [[input, answer], ...], { otherwise })]` stands in for function dependencies. A row lacking a stand-in, a `with` value not of the dependency's type, and a fake miss are row failures; malformed, duplicated or dead fake rows are `fakeIssues` and the table stands in for nothing. A function dependency may also be declared as another behavior — `dependency(checkStock)` or, to bring its recorded rows too, `dependency(checkStockExamples)` — taking that behavior's input and answering its result (effects are not part of the answer). Its `ensures` are then read against every fake row (a row that breaks one is a `fakeIssue`), and a fake row asked what a recorded row asks but answering differently is a `fakeWarning`, which does not affect adequacy.

3. **`src/specification.ts`** — the example/adequacy layer. `examples(behavior, { name: { given, with?, expect } })` builds a typed table of rows keyed by row name (duplicate names fail to compile; `Object.entries` order, so integer-like names come first), and `example(behavior, { given, expect })` types a single row built outside a table; where `expect` is either a concrete `Execution` or `todo(reason)`. `todo(reason)` is the one marker for anything not decided yet: an answer in `expect` (the row still runs, so it counts as executed but never as verified), a case in `cases` (running it throws `TodoDecision`; a row that reaches one is not a failure but a `row not run` in `incompleteness`, and a composition lists its stages' open cases as `<stage>: <case>` in `pendingDecisions`), or a control in `controls`; the report names it by where it sits (`unanswered`, `pendingDecisions`, `controlGaps`). `spec(name, { examples, implementation? })` ties an example set to an (optional) implementation. `check` is the core analyzer: it walks every example, tracks input/result/effect variant coverage, collects unanswered rows, pending decisions and control gaps, and — if an implementation is present — actually runs it against each example (`perform`) and deep-equal-compares the outcome, reporting mismatches as `failures`. The run-and-compare logic is factored into the private `runAndCompare` helper, shared with `test` below. The result is an `AdequacyReport`; `adequate` is true only when there is an implementation, zero failures/unanswered/pending/gaps, full input/result/effect coverage, and every class in `partitions` has an answered row in it. The report also carries `evidence` graded the way Souther grades it (an input case is `specified`/`executed`/`verified`, a result case `specified`/`observed`/`verified`; a row whose answer is owed still runs, so it can execute and observe but never specify), `measures.arms` (`not applicable` without an implementation, otherwise `not measured` with a `notRead` list of decision ids — a `Decision.run` closure is opaque, so its branches are never read), and a `verdict`: `not_satisfied` when a gap was found, `undetermined` when none was found but the arms could not be measured, `satisfied` only when nothing is left unmeasured. `--strict` exits 1 exactly when `adequate` is false; an unreadable measure is the tool's shortfall and never fails a build. `generate` emits `todo()` rows (with schema-derived placeholders) for every uncovered input variant and then for every class no existing or generated row stands in, moving only the position that class belongs to — this is what backs `chisel generate`. Rows whose answer is owed count as already asking, so they are not generated again. `test` is a separate, narrower check: it runs *only* the answered examples against an arbitrary async subject function (e.g. a real controller/service) and returns `{ failures, skipped }`, `skipped` naming each row left out because its answer is still `todo`, so a test decides whether an open answer may pass, keeping "does the model make sense" (adequacy) separate from "does infrastructure code conform to the model" (conformance).

4. **`src/cli.ts`** — thin politty wrapper over the above. Loads a spec file's module via `tsImport` (so `.ts` files run without a build step), discovers exported `Behavior`s and `Specification`s by shape (`isBehavior`/`isSpecification`), synthesizes an empty specification for any behavior that's exported but not wrapped in `spec` yet, and backs the `check` subcommand (prints `AdequacyReport`s) and the `generate` subcommand (prints ready-to-paste `example(...)` rows via `formatTypeScriptValue` from `src/codegen.ts`).

`src/partition.ts` derives the positions of a behavior's input from its schema, Souther-style: every field under each input variant is a position named by a path such as `@商品あり.クーポン` (`@` narrows to a sum case, `[]` steps into array elements, `?` into what an optional holds). `optional` divides into `なし`/`あり`, `boolean` into `true`/`false`, and a sum field into its cases; objects, array elements and optional payloads are taken apart recursively; everything else is `not-derivable` — the model draws no line through it, which is a fact about the model and never a gap. Record values are a position under `{}`. A `DividedPosition` can `classify` a given value and `place` a class into one (forcing the enclosing sum cases and writing an array element where needed); every position can `write` a coordinate, which is how `generate` composes rows — starting from the first answered row that reaches the position and moving only that position, falling back to placeholders. An array or record with no invariant of its own is not a position — only its elements are — but `positionsOf(input, { containers: true })` (used by `guardBordersOf`) keeps it as a `not-derivable` position so a guard on its `length` can still be composed by resizing it; a guard point `generate` still cannot compose is named in `notComposed` rather than dropped.

Invariants feed the same analysis (`src/border.ts`). An `eq`/`ne` rule on a boolean or on a sum field's discriminant `excluded`s the classes it refuses (counted as declared minus excluded). A rule comparing one coordinate — a value, or the `length` of a string/array/record — with a constant draws a `Border` on that position (an object invariant naming one field draws it on the field; one relating two fields draws none, and a position with borders but no classes is `bounded`). A border has the four domain-testing points: `ON`/`IN` are owed a row, `OFF`/`OUT` are `excluded` because nothing outside an invariant can be constructed, and `IN` is excluded where the rules leave that side one value wide. Whether a neighbouring value exists depends on the carrier: `int` and lengths step by 1 and `instant` by 1ns; `number` and `string` have no step, so their `OFF` point is `not named` and a strict bound on them draws no border. A rule naming one value (`eq`/`ne` against a constant) has a point on each side of it and reports the role it has no point in as `no point`. A point one invariant owes is `excluded` when another invariant on the same measure refuses its value (`withoutRefusedPoints`), and a position whose invariants on one measure then owe no point at all admits nothing: it is reported in `modelIssues` (which makes `adequate` false) instead of as gaps. Lengths use `lengthCarrier`, whose `floor` (0) turns every point lying wholly below zero — an `OFF`/`ON` value under 0, or an `IN`/`OUT` run below an edge at or under 0 — into `no point`, for invariant and guard borders alike. Invariants written on a sum (the behavior's input sum or a sum field) are passed down to every case like object invariants, so a rule naming a field the cases share draws its border on that field under each case; a rule on the input sum's discriminant excludes the input cases it refuses (`excludedCases`), which then drop out of `report.input` (listed in its `excluded`), of the input evidence, and of `generate`.

Guards feed it too (`src/guard-borders.ts`). A guard comparing a position with a constant draws a border whose `OFF`/`OUT` points are owed (both sides can be constructed) unless the position's invariants refuse them, and its thresholds divide the position into interval classes merged with the invariant range; an interval the invariant range leaves empty is listed in `excluded` rather than dropped. A guard comparing two positions divides neither and draws its border on their difference (integers, numbers, lengths, or instants in nanoseconds). An `eq`/`ne` between two positions draws no border and is not an unread comparison: following Souther, an equality between two positions puts a whole arm on each side of the line, so the arms and rules measures cover it; `between` returns no border for `==`/`!=` on purpose. A guard border point is met only by a row whose run reached that comparison, not by one that merely writes the value. Comparisons Chisel cannot read (e.g. two strings ordered against each other) are listed under `measures.comparisons`, which makes the verdict `undetermined`. `measures.arms` covers each guard's `holds`/`else` and each `match` case; `measures.rules` (`src/ways.ts`) covers each way through the guards, enumerated depth-first with short-circuiting. A way (and an arm, through the ways that pass it) no row took is classified by `src/feasibility.ts`: comparisons with constants are gathered per coordinate together with that position's invariants and settled on its carrier (a sum discriminant or boolean on its finite domain), and a comparison between two positions is settled on their intervals when each position takes part in at most one such comparison. A contradiction makes it `no row owed`; an `all`/`any` condition sharing a value with another step, or anything left unsettled, makes it `undecided`, which turns the verdict `undetermined` instead of `not_satisfied`. `generate` skips infeasible ways, and the CLI counts both states per reason instead of listing them. A guard border point no row met is settled the same way: its region (`BorderPoint.region`) is placed on the compared coordinate and checked together with the steps of each way before that comparison (`reachOf`; comparisons inside `all`/`any` and between two positions are not placed), so a point only reachable with values outside it — the points of `x >= 5` behind `x >= 10` in an `and` — is `no row owed` and `generate` offers no row there.

`src/composition.ts` provides `compose(name, [implementations...])` (Souther's `>->`): it takes two or more stage implementations and returns `[composition, implementation]`. Stages are folded left to right; each join is an ordinary `Behavior` whose input is the first stage's and whose result is the cases the earlier stages answer that the next stage's input does not take (they *depart*) plus that stage's result cases, carrying `pair` and `departed` (also in the type, so a departed case never reaches a later stage). The composition keeps its stage behaviors as `stages`. All result/input sums must share one discriminant, a tag that would both depart and be answered by a later stage is refused, a case flowing on to the next stage may not carry a field that stage's input does not declare (compared by keys at every depth through objects, array elements, optionals on either side, record values — an answered object's fields are compared with the record value the next stage takes — and nested sums, where a case the next stage does not declare, or a discriminant it names differently, is refused too; an answered sum taken as a plain object must have its discriminant and every case's fields declared there, and an answered object taken as a sum is compared with the case its literal discriminant names. The other direction is held too: a field the next stage requires (not `optional`) that the answered case leaves out or answers only as optional, including the discriminant of a sum the next stage takes, is refused as `<first> does not always answer <path>, which <second> requires`; a record the next stage takes requires no key, and an enclosing sum's discriminant always travels with the value, so neither counts. It is refused with its path such as `@有効.明細[].単価` or `@有効.支払@カード`; a sum's discriminant that the answered case declares for itself is not counted, and declaring the same shape twice is fine. Types are held too, on the rule that every value the answered schema allows must be one the taken schema takes: a leaf of another type, a container of another kind (a record taken as an object may carry any key, so it is refused), a literal of another value, a string taken as one literal and a number taken as an integer are refused as `<first> answers <path> as <kind>, which <second> takes as <kind>`, while an integer taken as a number is accepted, and a literal is judged by parsing its value with the taken schema (so `literal(Infinity)` taken as a number, or a literal a taken invariant refuses, is refused); a sum's tag is compared as a literal with the discriminant field the next stage declares (on a plain object or on the case object itself), whatever type the answered case declares for its own discriminant, since the value always carries the tag, an answered sum taken as a record has each tag and field compared with the record value, and an answered object taken as a sum must name its case with a string literal. Invariants are otherwise left to run time), effects and `requires` are united, and a composition carries no `ensures`. The returned implementation nests binary `pipeline`s; `runTraced` runs the first half and hands the answer to the second only when its tag is on the main line and the second takes it, concatenating effects. A composition's arms and rules measures are `not applicable`, and guard-derived borders/classes/unread comparisons are empty because its `cases` is. `external(behavior, reason)` (in `src/behavior.ts`) is an implementation Chisel never runs — distinct from `todo`, nothing is owed: `perform` throws on it, and `check`, finding one in an implementation (or any stage of it), records every row as `row not run` in `incompleteness` instead of running it, reports its arms/rules as `not measured`, and makes the verdict `undetermined`. `generate` prints, for a behavior whose specification has no implementation, an `implement` scaffold with every case and control `todo`.

`src/report-json.ts` projects `AdequacyReport`s into the `check --json` document (`reportDocument`): it adds `sources`/`source`, an `obligationId` to every border point, arm and way (disambiguated with `#n` when two read alike), and `weakening` to every measure that is `partial` or `unavailable` for want of something it could not read. Those JSON-only fields are kept out of the in-memory report on purpose; `schema/report.schema.json` is the closed schema of the document, and `test/cli.test.ts` validates real documents against it with a small validator (`test/support/json-schema.ts`) — adding a field to the report means adding it there.

`src/codegen.ts` is a small, standalone pretty-printer from runtime values back to TypeScript literal syntax (including `Temporal.Instant.from(...)`), used only to render generated example placeholders: keys are bare where they are identifiers (Unicode identifiers included) and every multi-line object/array item ends with a comma. `chisel generate` prints, for a behavior it had to synthesize a specification for, the `import ... from "chisel"` line (once per run) plus `examples(...)` and `spec(...)` blocks; for a real specification it prints only the rows, each ending with `,`.

## Key invariants to preserve when editing

- `variants`'s `parse` merges the discriminant tag back into the parsed value (`{ [discriminant]: tag, ...result.value }`) — variant object schemas do not need to declare the discriminant field themselves.
- Coverage/adequacy analysis (`check`, `generate`) depends entirely on `VariantsSchema.variantTags` and `tagOf`; if you add a new schema kind that can appear as a behavior's `input`/`effects`, it must stay a `VariantsSchema` or the coverage model breaks.
- `perform` and `check`'s implementation check both re-validate input/result/effects through the schema, even though the example row was presumably already schema-valid — don't remove this, it's what catches implementation code that returns malformed data.
- Stale examples are meant to fail to compile when the data/behavior model changes (see `examples/progressive-demo/type-break/`) — this is a deliberate correctness mechanism, not something to work around with looser types.
- `object()`'s `parse` refuses a key its shape does not declare instead of dropping it, so a model that answers with a stray field (say, spread from its input) fails `check` the way it fails `test`, rather than having the field vanish before the comparison.
- `object()`'s `parse`/`placeholder` drop a field entirely when its value is `undefined` (this is how `optional()` fields disappear instead of being written as `undefined`). Keep that: `check`/`test` compare examples with `isDeepStrictEqual`, which treats `{ note: undefined }` and `{}` as different — writing an explicit `undefined` key would make schema-normalized values fail to match hand-written examples that simply omit the field.

## The progressive demo

`examples/progressive-demo/` (driven by `npm run demo`, verified by `test/progressive-demo.test.ts`) walks the full stage-01 → stage-04 sketch/answer/refine/implement sequence for a hotel reservation behavior. It's the reference example for how the four stages are meant to compose in practice — read `examples/progressive-demo/README.md` and the stage files in order before changing the demo or the underlying API surface it exercises.
